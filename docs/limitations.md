# Interpretation and limitations

## Comparable controls

All UI runs use the same generated bytes, block counts, 1280x800 logical
viewport, one internal action warm-up, ten input actions and 120 scroll actions.
MoUI, GPUI, Flutter and Electron use fixed-height block virtualization; only
the active block owns a native/WYSIWYG editing surface and inactive visible
blocks are formatted previews. These controls are suitable for regression
detection and a coarse framework comparison.

## Timing clocks are not equivalent

- MoUI reports synchronous build/layout/paint/draw work plus Skia
  `render_frame` completion.
- GPUI reports intervals and action latency at `Window::on_next_frame`; this is
  not an OS compositor-present timestamp.
- Flutter reports engine `FrameTiming.totalSpan`; its input latency ends at
  `SchedulerBinding.endOfFrame`.
- Electron reports Chromium `requestAnimationFrame` intervals and action to the
  next rAF callback. This is not Chromium compositor tracing.

The generated 2x table is intentionally labelled a screen. It uses only
matching `ui-frame` fixture/scenario rows, but a ratio between different clocks
is still not proof of equivalent end-to-end presentation latency.

## Implementation boundaries

### MoUI

The interactive editor uses `MarkdownDocumentSession` and a constrained
virtual list so edits and scrolling do not format the full document. The GPU
adapter verifies a real GPU Skia surface (`metal-gpu` on this host and
Direct3D on Windows), but the benchmark presents through an offscreen/readback
`SkiaPresentTarget`, not an operating-system compositor surface. GPU numbers
therefore include this present path and can be slower than Raster.

The standalone `markdown_document` diagnostic recomputes source ranges with a
full-source character scan per block and scales super-linearly. Its
`richtext-full` row is capped at Small and must not be compared to UI frames.

### GPUI

The executable, UI command tree, document model, handlers and file operations
are MoonBit native code linked to the vendored `gpui-moonbit` Rust static
library over C FFI. Rust owns only the GPUI entities, native `InputState` and
window resources that cannot cross the C ABI directly.

On the audited host, the linker warns that several Rust static-library objects
target macOS 26.2 while the MoonBit link targets macOS 26.0. The app links and
runs on macOS 26.3, but compatibility with older macOS releases is not claimed.

Inactive and active blocks both remain visually formatted. While a block is
active, a formatted layer is painted under an input layer whose source glyphs
are transparent; GPUI still paints its caret and selection independently.
Caret hit-testing therefore follows raw Markdown offsets, so hidden `#`, `**`,
list and quote markers can create a horizontal caret offset near syntax. A
complete source-to-display offset map is outside this minimal benchmark.

### Flutter

The document is parsed once into blocks and rendered with `ListView.builder`.
Only the active block is an editable, syntax-highlighted `TextField`; visible
inactive blocks use a separate WYSIWYG `RichText` formatter. Every active span
preserves its source characters and text metrics, with muted Markdown markers,
so caret and selection offsets match the controller text. Profile runs are accepted only when
engine startup logs confirm the requested Skia or Impeller backend. The wrapper
retries one signal/renderer-validation crash and records the retry count.

### Electron

Electron uses Vditor 3.11.3 with `mode: "wysiwyg"` and local assets. The
comparison path mounts Vditor only for the active block and uses Vditor's bundled
Lute renderer for visible inactive blocks. This preserves formatted editing
while bounding DOM size for the 5 MB Stress fixture. Chromium's process model
still has different memory/startup costs from the native block editors.

## Markdown subset

The native comparison renderers cover headings, paragraphs, bullet lists,
blockquotes, fenced code, emphasis and inline code. Tables, images, raw HTML
and advanced extensions remain editable source text. Electron/Vditor supports
more syntax, but the shared benchmark fixtures stay within the common subset.

The block-oriented implementations parse and serialize Markdown when saving.
They retain the document's Markdown meaning and unsupported source text, but
may normalize blank lines, trailing spaces and other insignificant whitespace;
byte-for-byte source round trips are not part of this benchmark contract.

## Result sets

`results/macos-arm64-local.json` and `.md` are the earlier renderer-neutral
`headless-render` capture. They remain useful diagnostics and must not be
renamed or interpreted as UI measurements. The desktop UI-process capture is
written separately as `results/macos-arm64-ui.json` and `.md`.

The regenerated macOS UI-process capture is complete (252/252 measured, 0 errors:
seven adapters x four fixtures x three scenarios x three repetitions) and
retained as `results/macos-arm64-ui.json` plus its Markdown report. Windows
amd64 numbers are not synthesized on macOS. The same UI script and CI artifact
path are provided, but the dedicated 16 GiB Windows acceptance capture remains
pending until run on a real Windows amd64 host.
